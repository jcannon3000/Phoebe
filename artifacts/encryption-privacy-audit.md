# Phoebe — Encryption & Privacy Audit (2026-06-18)

> Generated by a multi-agent audit workflow: 54 findings mapped across 8 axes, 14 high-severity upheld after adversarial verification.

## Headline

No — today, anyone with database/Railway/server access (i.e. the platform builders) can read essentially all private user content in cleartext: journal entries, 1:1 direct messages, letters and unsent drafts, daily "prayer for the day" exchanges, private gratitude entries, prayer requests, and life events are all stored as plain Postgres text columns with no application-layer encryption. The ONLY content that is genuinely unreadable by platform builders is voice memos, which are correctly end-to-end encrypted (client-held key, server sees only opaque ciphertext). The protections the app actually has — TLS/WSS in transit and Railway's default disk encryption at rest — do NOT keep builders out, because both terminate at infrastructure the builders control; the one server-key column encryption (encryptedText) is applied only to Google OAuth tokens and is decryptable by anyone holding the TOKEN_ENC_KEY env var. To make journals/messages/prayers unreadable by builders requires extending the existing voice-memo E2E pattern (user_public_keys + voiceCrypto.ts) to text — a product/architecture decision, not a quick fix. Separately, several leaks make this worse than "DB-only": the 1:1 message preview is sent in cleartext to Apple's APNs, a password-reset token (a live account-takeover credential) and full prayer-request/event text get written to server logs on certain failure paths, and one IDOR lets a Fellow/garden-peer read a parish "pastoral concern" via the by-id route — all of those are safe to fix now.

# Phoebe Privacy & Encryption Audit — Definitive Report

## The bottom line

The owner's goal is that private user content be unreadable **even by the platform builders** (anyone with server/DB/Railway access). **That goal is currently met for exactly one content type: voice memos.** Everything else — journals, messages, letters, daily prayers, gratitude, prayer requests, life events — is stored as **plaintext** and is fully readable by builders.

The critical distinction, applied throughout:
- **TLS/WSS in transit** → protects against network eavesdroppers only. Terminates at Railway; the server then has plaintext. **Does NOT stop builders.**
- **At-rest disk/column encryption with a SERVER-held key** (Railway disk encryption; the `encryptedText` type keyed on `TOKEN_ENC_KEY`) → protects against stolen-disk/raw-dump theft only. The server/builders hold the key. **Does NOT stop builders.**
- **End-to-end encryption with a CLIENT-held key** (voice memos: `voiceCrypto.ts` + `user_public_keys`) → server sees only ciphertext, private key never leaves the device. **This is the ONLY thing that stops builders** — and it's applied to nothing but voice memos.

## Findings grouped by threat model

### THREAT 1 — Platform builders can read content (the owner's core concern) — CONFIRMED, BROAD

This is the headline failure. **No user content except voice memos is encrypted at the application layer.** Confirmed by repo-wide grep: the `encryptedText` type is applied to *exactly two* columns (the Google OAuth tokens in `users.ts:19-20`) and uses a **server-held** key; no other column has any app-level encryption, and the only client-side crypto (`voiceCrypto.ts`) is wired solely to voice memos.

Per-surface (all HIGH, all `at-rest`, all readable by **anyone with Postgres/DB/Railway access**):
- **Journals** — `journal_entries.body` plaintext; client posts raw string (`journal.tsx:115-116`); strongest E2E candidate (author-only, no recipient → symmetric self-key suffices).
- **1:1 messages** — `beta_messages.body` plaintext; known recipient → maps directly onto the voice-memo ECDH model.
- **Letters + drafts** — `letters.content` / `letter_drafts.content` plaintext; the list endpoint even runs `substring(content …)` in SQL, only possible because it's cleartext. Member PII (email/name/city/country) also plaintext.
- **Daily prayers** — `daily_prayers.body` plaintext; the "seal until morning" is only a read-time filter (`deliver_after <= now()`) — the full plaintext is written at insert and immediately builder-readable.
- **Gratitude (private)** — `gratitude_responses.text` plaintext even for `shared=false` rows the user expects to be author-only.

NOTE on already-correct **application-layer authz**: over the API, these surfaces are properly owner/membership-scoped (journal owner-only, gratitude `shared=false` never leaks to other users, messages gated by `requireMembership`, prayer-partner by `arePartners`, etc.). So *other app users* cannot read this content through the API. The gap is purely that **builders bypass the API and read the DB directly** — which only E2E prevents.

### THREAT 2 — Off-platform content egress (worse than "DB-only")

- **1:1 message preview sent in cleartext to Apple APNs** (HIGH, `push`). `beta-messages.ts:313-318` passes `preview: parsed.data.body.trim()` (raw message text); `pushSender.ts:1058-1072` puts up to ~139 chars into the APNs `alert.body` → POSTed to `api.push.apple.com`. **Apple sees the cleartext message.** (Web-push payloads are RFC-8291 encrypted, so browser-vendor push services do not see plaintext — the exposure is specifically the APNs path.) **Safe to fix now** by making it a generic knock.
- Self-authored "Bless" intention and short life-event/plan **titles** also flow through APNs (LOW) — short, user-chosen, lower sensitivity.
- **No analytics/attribution/advertising SDK anywhere** ✅ — only Apple (push), Google (email/OAuth), Sentry (errors) are outbound. Letter emails carry **no** letter body (knock + link only) ✅. LLM/transcription vendors (OpenAI/Anthropic) receive only **public liturgy**, never user content ✅.

### THREAT 3 — Server log leaks readable by builders

- **Password-reset URL + token logged on email-send failure** (HIGH, `secrets`) — `auth.ts:1160` logs the full `…/reset-password?token=<256-bit token>`; that token is a **complete ~1-hour account-takeover credential** (no email re-verification). Full email also logged at several lines. **Safe to fix now.**
- **Prayer-request POST logs full `req.body`** (prayer text + event title) on schema-validation failure (HIGH, `logging`) — `prayer.ts:787-792`; fires on legitimate oversized/old-client input, not just abuse. **Safe to fix now.**
- **Push-sender stub logs the ENTIRE payload** (incl. the 1:1 message preview, life-event titles, names) when `APNS_*`/`VAPID_*` are unset (HIGH, `logging`) — `pushSender.ts:337-341, 400-406`; this is the documented dev/preview-deploy default and triggers on any prod cred lapse. **Safe to fix now.**
- Every push send/skip logs **recipient email + push title** (MEDIUM); OG-preview failures log **raw share/dialogue tokens** (MEDIUM); email library logs **full recipient addresses** (LOW). All **safe to fix now**.
- Already-OK: the messages, journal, gratitude, letters, and voice-memo routes have **no** content logging at their own layer; pinoHttp strips query strings and redacts auth/cookie headers ✅.

### THREAT 4 — Cross-user (IDOR / access control)

- **Parish "pastoral concern" readable by any Fellow/garden-peer via `GET /prayer-requests/by-id/:id`** (HIGH, `access-control`) — **CONFIRMED**: the detail route (`prayer.ts:53-83`) never checks `parishFeedId`; the only gate is the garden/tagged check, so anyone sharing a group with the owner (or a Fellow) reading a guessable sequential id gets the concern body. The **list** route correctly excludes parish rows for non-owners (`:416-419`), proving intent — the detail route is strictly more permissive for the same private data. **Safe to fix now** (mirror the list route's parish gate).
- **Letter invite token = perpetual bearer capability** (MEDIUM) — `letterAuth.ts` honors `?token=` and impersonates the member forever, no expiry/session binding. And membership matches on **case-folded email** (LOW), so registering an unclaimed invited email could grant read access. Both `needs-product-decision` (changes the no-login letter-link flow).
- Otherwise, READ-path authz is **solid** ✅: journals/gratitude/messages/prayer-partner/prayers-for/fellow-plans/voice-memos and the prayer-request list + owner-only routes were all verified correctly scoped, including share-token routes being deliberate opt-in capabilities.

### THREAT 5 — Device theft / local storage (NOT builder-readable, but real on a shared/stolen/XSS'd device)

- **Voice-memo E2E private key in plaintext `localStorage`, exported as extractable JWK** (MEDIUM, `device`) — `voiceCrypto.ts:21,38-52`. Server still can't decrypt (key never leaves device), but device theft or XSS exfiltrates the JWK → decrypts all incoming memos. `needs-product-decision` (non-extractable IndexedDB key / iOS Keychain plugin).
- **Persistent auth token in plaintext `localStorage`; claimed native Keychain mirror does NOT exist** (HIGH, `secrets`) — `persistentAuth.ts`; the token exchanges for a fresh session at the anonymous `/api/auth/exchange-token` endpoint = full account takeover. grep confirms **no** Keychain/SecItem code in the iOS project; the in-code "mirror" comment is aspirational. (It IS revoked + cleared on explicit logout ✅.) `needs-product-decision`.
- **Logout wipes only 4 keys**; private content caches + the voice key persist for the next person on a shared device (MEDIUM). React Query persister (`phoebe:rq-daily`) and IndexedDB offline cache hold prayer/moment bodies in plaintext (MEDIUM/LOW) — both cleared on explicit logout, but not on account-switch. **Safe to fix** (whitelist-clear).
- iOS uses **no** Keychain/Secure Enclave anywhere; everything device-side is WKWebView localStorage/IndexedDB or App-Group UserDefaults (the latter only for widget/health bridges, not content/secrets).

### THREAT 6 — In-transit / session (network attacker, NOT builders)

- TLS/WSS present but in-transit only; terminates at Railway, server then has plaintext (INFO — expected).
- No app-level HTTP→HTTPS redirect (LOW) — delegated to Railway edge; HSTS emitted in prod. `SameSite=None` in prod relies on the (tight) CORS+CSRF allowlist (LOW). CSRF fails open when both Origin and Referer absent (LOW — not exploitable via standard browsers).
- Already-OK ✅: `/ws` is session-authenticated against the same cookie and never trusts client-supplied `user_id`; CORS is a strict allowlist (no wildcard reflect); session cookie HttpOnly + Secure-in-prod; prod refuses to boot without `SESSION_SECRET`; HSTS + standard security headers present; body-size limits + 413 handler.

## What is already done right

- **Voice memos are genuinely E2E** — server stores only opaque ciphertext + IV + ephemeral public key; recipient's static private key never leaves the device; ciphertext deleted on listen + 48h TTL. This is the **reference architecture** to extend.
- **Cobreathe coarse location is never persisted** — in-memory-only on the ephemeral WS session.
- **Passwords**: scrypt + 16-byte per-user salt + `timingSafeEqual`.
- **No analytics/ad/attribution SDKs** anywhere; client only talks to its own API.
- **Secrets hygiene**: `.env` and `*.p8` are gitignored, never committed, never in build output or client bundle; APNs/VAPID/admin keys read from env, not hardcoded. (Two working-tree caveats below.)
- **Strong application-layer authz** across all private read paths (Threat 4).
- **Sentry** is server-only, bodies-off, console-breadcrumbs-off, scalar tags only.

## Needs product decision (NOT applied — irreversible / data-loss tradeoffs)


### 1. End-to-end encrypt journals (author-only) and 1:1 messages + daily prayers + voice-memo-key hardening — the core of the owner's goal
**Why hard:** These tables are plaintext today and only client-held-key E2E keeps platform builders out (TLS and server-key column encryption do NOT). The hard parts are (1) KEY RECOVERY = DATA-LOSS RISK: if the client key is the only thing that can decrypt and the user loses their device/clears storage with no recovery path, their journals/messages are permanently unreadable — a recovery scheme (passphrase-wrapped key escrow, or a recovery code the user must save) is a real product decision with its own security tradeoffs; (2) it BREAKS server-side features that read the body: the SQL substring() letter previews, any content moderation, and notably the push/notification previews and any future server-side search — these must be reworked to operate on metadata/timestamps only (unread counts already work off timestamps, so those survive); (3) migration: existing plaintext rows can't be retroactively E2E-encrypted without each user's device re-encrypting on next login.

**Recommended path:** Phase the rollout, reusing the PROVEN infra (user_public_keys + voiceCrypto.ts; the platform already ships ECDH→AES-GCM E2E for voice memos — it just hasn't applied it to text). PHASE 1 (lowest risk, highest value): journals — author-only, no recipient, so a symmetric key derived from the user's own keypair/passphrase suffices; no multi-recipient complexity. PHASE 2: 1:1 messages and daily prayers — a known single recipient maps directly onto the voice-memo ECDH-to-recipient model; ship the generic-knock push fix (safeFixes) FIRST so removing the preview isn't a regression. PHASE 3: letters and letter_drafts — drafts are author-only (E2E like journals); sent letters can fan out to small groups, needing an encrypt-content-key-to-each-member scheme (more complex) — do this last. Treat open-membership/community surfaces (forum, group reflections, public prayer requests, gratitude shared=true) as out of scope for E2E — their recipient set is dynamic and they are shared-by-design; document them as server-readable. Before Phase 1, decide the key-recovery story (recommend a user-saved recovery code + optional passphrase-wrapped escrow) because that decision shapes every phase.

### 2. Key-recovery model for any E2E content (decide before shipping Phase 1)
**Why hard:** True E2E means the server cannot help a user who loses their key — so 'forgot my device' becomes 'lost my journal forever' unless there is a recovery path, and every recovery path reintroduces some attack surface (an escrowed key the server can wrap, a recovery code the user might lose, or accepting permanent loss). This is the single decision that most affects user trust and support burden.

**Recommended path:** Recommend: generate a non-extractable device keypair PLUS a user-held recovery code (shown once, user must save it) that wraps a backup of the content key; optionally allow passphrase-derived escrow for users who want server-assisted recovery, clearly labeled as 'we cannot read your content but a forgotten passphrase means lost content.' Match the voice-memo hardening here too: move the voice private key off plaintext localStorage to a non-extractable IndexedDB CryptoKey (web) / iOS Keychain via a Capacitor plugin, and wipe it on logout.

### 3. Persistent auth token storage + claimed-but-missing native Keychain mirror
**Why hard:** The persistent token is a full account-takeover bearer credential sitting in plaintext WKWebView localStorage; the in-code comment claims a native Keychain/Capacitor-Preferences mirror that grep proves does NOT exist (no Keychain/SecItem code anywhere in the iOS project, and Capacitor Preferences writes to App-Group UserDefaults which does not share storage with WKWebView localStorage). Fixing it correctly requires writing a native plugin, which is product/eng scoping, not an unattended edit.

**Recommended path:** Implement an iOS Keychain-backed store (kSecAttrAccessibleWhenUnlockedThisDeviceOnly) via a native Capacitor plugin and expose the token to the web layer only at exchange time; treat the existing 'mirror' comment as aspirational and stop relying on localStorage as the source of truth. As an interim safe step, hash the persistent_auth_tokens.token column server-side (see safeFixes) so a DB/log leak can't replay it.

### 4. Letter invite-token capability model (perpetual bearer token, email-based membership)
**Why hard:** Letters must work from an emailed no-login GET link, so the token currently acts as a forever-valid bearer capability and membership also matches on case-folded email — meaning a leaked invite URL, or registering an unclaimed invited email, can grant read access to correspondence bodies (which are also plaintext at rest). Tightening this changes the frictionless no-account letter-link UX.

**Recommended path:** Once a member row has a real userId (joined account), require session auth for that correspondence and stop honoring the token path for reads; reserve the token-as-capability only for not-yet-registered invitees, and expire/rotate invite tokens after first successful join. Prefer userId-based membership matching, falling back to email only for pre-join rows with verified email ownership. This is a security/UX tradeoff to decide deliberately rather than auto-apply.
